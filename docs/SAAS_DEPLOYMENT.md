# SaaS deployment and operations

These files package a single-host deployment; no public host, certificate, OAuth project, bucket, paid resource or provider inference was created. Compose is an operator-run template, and CI validates only. Public release still requires actual-host security/privacy/recovery evidence in `docs/DEPLOYMENT.md`.

## Services and boundaries

`services/api/Dockerfile` installs the frozen Python lock and runs as uid10001. `Dockerfile.frontend` builds Next standalone and a separate credential-free executor image with frozen pnpm dependencies and hash-verified analytical assets. Base Node/Python/uv and PostgreSQL images are digest-pinned. API uses one worker, three pooled DB connections, zero overflow and bounded connection/statement/lock timeouts. Multi-instance admission and distributed authentication throttling remain separate release work.

`compose.production.yaml` gives API, web and executor read-only filesystems, dropped capabilities, no privilege escalation, bounded temporary filesystems, memory limits, healthchecks and capped logs. PostgreSQL has a private volume/internal network and no published port. Only API joins an egress network for allowlisted provider/OAuth/storage calls. Web and executor join separate internal networks and publish loopback ports3000/3001; API publishes loopback8000. A TLS reverse proxy on the same host is required. Docker network isolation does not replace browser worker CSP or API destination policies.

PostgreSQL's official entrypoint initializes volume ownership as root, then runs PostgreSQL as its postgres user. It cannot use the same read-only/capability restrictions as the application images during first initialization. Its initialization credential is a private file mounted under `/run/secrets`; Compose file secrets are host-file mounts, not an encrypted secret manager.

The three canonical origins must be exact origin strings without credentials, paths, queries, fragments or trailing slash. Public HYPOTHRON_DEPLOYMENT=1 requires HTTPS and distinct hostnames; the existing HYPOTHRON_PRODUCTION local browser-test flag remains independent. Use a separate registrable executor domain (for example app.company.example and compute.company-compute.example); never set parent-domain authentication cookies that reach the compute hostname. Executor receives only origins/HOST/PORT, never API env files, database credentials, OAuth secrets or provider keys. Its main worker retains `connect-src 'none'`; nested DuckDB worker additionally retains `worker-src 'none'`. The host page allows only its own bootstrap assets and exact app frame ancestor.

## Configure, migrate, run

1. Copy `scripts/deployment/env.example` to a private operator directory and set the exact public app/API/executor origins. Put private API and migration environment files outside the repository, mode0600, parent directory0700. Put the database initialization password in a separate mode0600 file. Do not use the user's hosted database for local validation. Do not run unfiltered `docker compose config`, inspect container environment or dump `.env` values into logs.
2. The migration file contains only a privileged migration `DATABASE_URL`; the API file contains a separate runtime role's `DATABASE_URL` and required backend configuration. URI-encode credentials. The runtime PostgreSQL login must have `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`, CONNECT to this database, USAGE on its application schema and required table/sequence permissions. LangGraph initializes its native checkpoint tables; its current runtime setup needs CREATE on the application schema. Provision the role before API startup, then grant current tables and migration-owner default privileges. No runtime login should use the PostgreSQL initialization superuser. Use a secure interactive `psql` session and `\password` or your secret manager to set passwords; never paste passwords into tracked SQL or shell arguments.
3. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_REDIRECT_URI=https://api.your-domain.example/v1/auth/google/callback` in the API file when enabling Google OAuth. Register that exact callback in Google Cloud. The implementation owns bounded flow state and identity verification; mocked tests do not establish a working external OAuth configuration. Inference remains BYOK; deployment adds no shared platform inference key. Optional cloud storage uses backend-only CLOUD_STORAGE_ENABLED, S3_ENDPOINT_URL, S3_REGION, S3_BUCKET, S3_ACCESS_KEY_ID and S3_SECRET_ACCESS_KEY. Require a private bucket, encrypted writes and prefix-scoped access. Keep cloud persistence disabled until the private storage destination, credentials and encryption policy have been explicitly configured and verified.
4. Run `bash scripts/deployment/validate.sh`. Build images with the non-secret origin build arguments. Both web and executor embed origins; changing public origins requires rebuilding both images with matching runtime executor settings.
5. After separately authorizing deployment, set `DEPLOYMENT_ENV_FILE=/secure/hypothron/deployment.env` and run `bash scripts/deployment/launch.sh`. The one-shot `migrate` service runs `alembic upgrade head`, and API starts only on its success. Do not run downgrade/restore against production as a trial. On subsequent releases explicitly rerun migrations for the new image before promoting API traffic; review migration compatibility and preserve an encrypted backup first.

For local development only, `scripts/run-api.sh` accepts an explicit `DATABASE_URL`, or loads a private `API_ENV_FILE` (default root `.env`) through uvicorn dotenv. It does not source arbitrary shell expressions or print the environment. This convenience does not permit use of hosted credentials in test commands.

## TLS proxy and external checks

Terminate TLS for each hostname and proxy exclusively to its corresponding loopback port. Preserve executor CSP/Referrer-Policy/nosniff headers exactly; never inject analytics, cookies, authentication or third-party scripts on executor. API proxy must disable buffering for SSE, preserve cancellation/disconnects, bound request bodies, use sufficient bounded stream timeouts and strip client-supplied forwarded headers. The app intentionally disables Uvicorn proxy headers; use explicit configured callback/origins rather than deriving security destinations from request Host. Apply HSTS after HTTPS is proven. Do not expose Docker's API or PostgreSQL.

Exercise authentication ownership, login/logout/OAuth callback, Save consent, cloud object integrity/size/quota/deletion, provider-key redaction, bounded cancellation, restart/checkpoint recovery, exact CSP/CORS/postMessage origins, real numerical verification and zero-inference replay on the actual TLS origins before publication. Proxy/certificate/bucket DNS and public browser policy have not been validated locally. Object-store encryption/access lifecycle requires explicit private-bucket credentials and policy; credentials and dataset bundles must never reach public web/executor images.

## Backup and recovery

Metadata and account/checkpoint/aggregate records are sensitive. `backup.sh` requires an existing mode0700 non-symlink directory, uses umask077, makes a mode0600 custom-format PostgreSQL dump and deletes partial output on failure. It does not output connection URLs or fetch provider credentials. No automatic plaintext upload exists. Keep local dumps on an encrypted disk; encrypt before off-host transfer using an operator-held recipient key (for example `age -r RECIPIENT_KEY -o backup.dump.age backup.dump`). Store encrypted backups in an explicitly private destination with restricted restore identity, independent retention and audited access. Keep keys separately from backup storage. Securely retire plaintext according to filesystem/volume policy; `rm` alone is not an erasure guarantee. Cloud bundle objects, OAuth/client secrets and local IndexedDB are separate from PostgreSQL backups; include private object-store backup/lifecycle and secret-manager recovery in the runbook.

Use `DEPLOYMENT_ENV_FILE=/secure/hypothron/deployment.env bash scripts/deployment/backup.sh /secure/hypothron/backups` after authorization. Test recovery with `bash scripts/deployment/restore-drill.sh /secure/hypothron/backups/FILE.dump`. The drill always creates a fresh disposable PostgreSQL17 container with network disabled, no published port, no shared volume and no hosted connection URL; it restores with exit-on-error, reports table count/revision and removes only its own container. Its temporary trust setting is restricted to this isolated drill container. Restoring untrusted SQL dumps executes their SQL inside that disposable boundary; accept backups only from your own trusted producer. Verify representative owner-scoped rows, checksums, protocol records and object consistency before promoting any recovered production database.

A local real custom-format dump/restore against the test-owned PostgreSQL succeeded on2026-10-14: the initial revision0001/six-table snapshot and revision0005_account_history/fifteen-table and final revision0006_cloud_intents/fifteen-table snapshots restored into fresh network-disabled PostgreSQL containers. This demonstrates final-schema restore mechanics locally; hosted recovery, object-store consistency and representative row checks remain external release gates. No numerical RPO/RTO or backup durability promise follows from one local drill.

## Rollback and validation evidence

Record image digests, source commit, applied Alembic head, origins and runtime asset manifest in release records without secrets. Retain the previous compatible image. Roll back application images only when their expected schema is compatible; otherwise restore into a new isolated database, verify integrity and explicitly approve traffic promotion. Never blindly downgrade a live schema or delete its volume. A healthcheck proves reachability/readiness, not cross-tenant security or full functionality.

`tests/deployment` checks canonical HTTPS origin rejection/redacted failures, private backup directory refusal, real configured executor frame ancestors and denied worker egress. `scripts/deployment/validate.sh` runs those tests, Bash syntax, ShellCheck when installed and secret-safe Compose validation using synthetic settings. ShellCheck is optional for local convenience; the existing CI static gate installs/requires it. API, web and executor images built locally and passed non-root/read-only readiness smoke checks; the final web public-font COPY correction was added after that image smoke and was not rebuilt because of host disk pressure. The final0006 private database dump restored successfully into an isolated PostgreSQL container. These local checks do not prove actual-host deployment. Docker builds legitimately download locked packages/runtime wheels; they never invoke provider inference.
